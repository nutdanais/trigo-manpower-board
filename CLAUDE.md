# Notes for Claude

- **Share files as GitHub links.** When you hand the user a SQL script (or any other file from this repo), give a GitHub link to it on the working branch (`https://github.com/nutdanais/trigo-manpower-board/blob/<branch>/<path>`, plus the `raw.githubusercontent.com` link for copy and paste). Do not rely on links to files inside the session; they often do not open for the user.
- **Share HTML pages as a viewable link, without being asked.** Whenever you make an HTML page for the user (design directions, mockups, reports), publish it as a claude.ai Artifact, open it in the session (Artifact `open`) so it shows right away, and give that link first, so it opens rendered in the browser. Also commit the source under `design/` and add the GitHub link. A GitHub `blob` or `raw` link alone only shows source code, so it is never enough for an HTML page.
- **Name PRs after the change.** A PR's title says what the PR actually changes (e.g. "Phone: Overview, Manpower and Host match the board's header"), not the task it started from. When later commits change the scope (a design-only PR that then gets the implementation), update the title and description in the same turn as the push.
- **Name branches after the change.** Don't push to a generated branch name like `claude/gallant-fermat-9wdq37`. Before the first push, create a branch named from the session's title in kebab case under `claude/` (session "Mobile/desktop design consistency review" → `claude/mobile-desktop-design-consistency`), and push and open the PR from that branch. This is the user's standing permission to use that branch instead of the assigned one.
- **HTML pages are light mode only, like the app.** Design pages, mockups and reports use the app's light palette and declare `<meta name="color-scheme" content="light">`. Give them no `prefers-color-scheme: dark` or `data-theme="dark"` styles, so they don't turn dark on a device set to dark mode.
- **Keep the demo working, and link its preview.** The app can run on invented sample data in the browser at `/?demo` (see "Demo and training" in the README), and the user previews updates that way: every PR gets a Netlify deploy preview, and `<preview-url>/?demo` shows the change with no real database. So a user-visible change must also work there: when it needs a new table, column, RPC or trigger behaviour, extend `demo/fake-db.js` to imitate it (as the tests already do for loans, highlights and exit reasons), and add examples to `demo/seed.js` if the feature needs data to show. Run `node tests/e2e/demo-mode.e2e.js` with the other tests. In the PR description, give the preview link with `/?demo` (the deploy-preview address is in Netlify's comment on the PR; if it is not there yet, say the link follows once Netlify has built it). Say plainly what the demo does not prove: the real SQL and migration, row-level security, live sync between people, and real data.
