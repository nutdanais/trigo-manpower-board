# Manpower Management Board

A drag-and-drop daily manpower planning board (replacement for Microsoft Whiteboard).

## How to run

This app is now backed by **Supabase** (cloud database + auth + realtime sync), so it needs one-time setup — see [`SUPABASE_SETUP.md`](SUPABASE_SETUP.md).

Once `config.js` has real Supabase credentials, double-click **index.html** to open the app, or serve the folder with any static web server. Sign in with your `@trigo-group.com` account — or use **Request access** on the sign-in screen and wait for an admin to approve you.

## How to use

- **Boards**: tabs at the top-left. `+ Board` creates a new board (e.g. Rayong). Double-click a tab to rename it.
  - Every employee belongs to exactly **one board** — a card assigned on Non-Rayong can never appear as available on Rayong.
  - **Right-click** an employee card → Assign to a mission, send to a leave type, or return to Standby/Available On-call — the same as dragging, for when the target has scrolled off-screen or you're on touch — plus Edit / Move to another board / Deactivate. (Position, contract type, and service area move to the Manpower List tab — set them one at a time from Edit Employee, or in bulk from the list's selection bar.)
  - **Active / Inactive** — the **Status** column in the Manpower List toggles an employee on or off the roster (right-click → **Deactivate**, the Edit Employee modal's **Deactivate** button, and the list's bulk **Deactivate** all do the same thing). An inactive employee disappears from **today's and future** boards — the Standby / On-call pools, mission and leave cards, and every count built from them — so they can't be planned in. **Past dates keep them**, so a finished plan stays an accurate record of who was actually there. Nothing is deleted: flip Status back on and they return everywhere. The list header shows how many are inactive, and the column sorts, so they're easy to find again.
- **📊 Overview tab**: a management dashboard, not a wall of numbers — a KPI strip, a deployment donut + per-board stacked bars (with the "Needs attention" list of unassigned names right after), a contract-mix donut per board, a service-area breakdown (one bar per area on a shared scale — full length is that area's headcount, the two segments split permanent / on-call), two 7/14/30-day trend lines per board (click a legend entry to hide/show its line) — **Utilization** and **On-call availability** (on-call headcount not on a mission or on leave) — both counting only working days (weekends and holidays excluded), and a leave-by-type breakdown at the bottom. Every chart has a hover/focus tooltip with the exact numbers.
  - **How utilization is counted**: assigned ÷ (headcount − leave − holiday − **free on-call**). On-call staff are surge capacity, so an on-call employee who wasn't called leaves the denominator rather than dragging the day down — a day where everyone you actually needed is deployed reads 100%, however many on-call people went uncalled. They're still counted the moment they *are* deployed, and "On-call free" keeps its own stats-bar chip and its own **By board** column, so the number is never hidden.
  - Boards with employees still **Available (not assigned)** keep the amber "Needs attention" list of names, right after the Deployment chart — assign them to a mission or drag them to Standby. Click a name to jump to that board.
- **Date**: top-right button opens a calendar. Each date has its own saved plan.
  - **On login the board always opens on the next working day** — tomorrow, skipping that board's weekend days and any dates marked as holidays. It does remember which board tab you were last on, just not which date, so you always start on a day you can actually edit rather than on yesterday's finished (read-only) plan.
  - Future date with no plan yet → starts **empty**. Nothing is copied in automatically: the board shows a prompt with a **↺ Carry over last working day's plan** button (also the toolbar's **↺ Carry over** button), and only that explicit click brings the last working day's missions + crew in. This is deliberate — a plan is only ever changed by a real user action, so opening or exporting a board can never silently rewrite it for everyone else.
  - **↺ Reset Board** (toolbar): once a day has content, the same button becomes a destructive "start over from the last working day" — it confirms first, since it replaces what's there.
  - Past date → read-only 🔒; trying to edit shows a confirmation popup.
- **Forward planning — confirmed vs forecast.** A *confirmed* plan exists up to each board's **next working day** (tomorrow, or Monday from a Friday; holidays count). Every later date opens as a **FORECAST**: the board bar says so, the cards are dashed, and Export / PDF / Lock are gone. A forecast is tentative and lives in its own tables — it never reaches the confirmed board, Overview, Org Chart, the export or the Host Record until someone merges it.
  - **Start from confirmed** fills an empty forecast day from the latest confirmed working day. **Add Mission** (as on a holiday) lists that day's missions so an engineer ticks only the ones they will work on, optionally with their crew; people already placed on that forecast day stay where they are, and missions the forecast already has can't be added twice. **Copy forecast** copies it onto the next N working days that have no forecast yet (never over someone's work).
  - Placing someone is a **hold**. Moving a person another engineer holds asks first ("Held by … in mission 123"), then flags that engineer's mission red — "1 person taken by …" — until someone **acknowledges** it. The engineer who lost the person also gets a live toast and a "⚠ holds taken from you" counter in the board bar, so it isn't missed if they were offline.
  - When a forecast day becomes the next working day, the planner carries over as usual; if a forecast exists the app offers **Review & merge**: the carry-over and the forecast **side by side**, one row per mission (then Leave and Standby), each person as a small card. Wherever the two disagree the card is flagged, and the planner clicks it on the side to keep — per person, per changed mission detail (a new start time can be taken while the old engineer stays), and per mission added or left out. Hovering a card shows where that person is on the other side; each forecast card carries its forecaster's colour, and a filter narrows the review (and the "keep carry-over / take forecast for all" buttons) to one forecaster. Nothing that collides is decided for the planner — **Apply** points at what is left until every difference has a side — only moves off Standby and new missions start on the forecast side, since they overrule nobody. A confirm step shows the crew sizes that change and who will be alerted; only the chosen side is written. The forecast is kept, read-only (**View**).
  - **Alerts to the forecaster**: every part of a forecast that was not used — a person kept where the carry-over had them, a mission detail, a new mission not added — sends the engineer who forecast it an alert, with the planner's optional reason (quick picks or free text). It uses the same live toast, "⚠ … not used at merge" counter and **Acknowledge** as a taken hold, and opens as a visual breakdown: how many of their people were placed as planned, and per mission their forecast crew against the crew now on the board, with each change drawn as forecast → board.
  - **Merge decisions**: the "Forecast merged" note on the day counts what was not used and opens the full log — every decision, both sides, the result, the forecaster and the reason. Alerts and the log need `supabase/migration-2026-09-29-forecast-merge-review.sql`; without it the side-by-side review still works, it just can't tell anyone.
  - **Stale carry-overs**: a confirmed day that was carried over shows a banner when the day it was copied from has been edited since (or a newer working day now sits in between). **Review changes** lists the differences against a fresh carry and applies only what you tick — nothing else on the day moves. **Reset Board** still exists, but it is the heavy-handed option now.
  - The database also refuses confirmed missions/assignments more than 10 calendar days ahead — a backstop against a buggy client, not the rule people see.
- **Capacity tab**: numbers, not names — for **one board at a time** (pick it with the board switch in the toolbar), how many people each host (site) needs per shift and working day, against how many are available. The chart shows each day's available people as a grey bar with the demand inside it — navy where it is covered, **red on top where it is not** — and under it the **Gap** as a chip: **▼ red** when short, **● amber** when there is 0–1 to spare, **▲ green** otherwise. The stats row sums it up (short days, biggest gap, peak demand, roster); hover a bar for the permanent / on-call split, leave and how many are already named on the board. Every day is tagged **CONFIRMED** (the real board, up to the next working day) or **FORECAST**. **Named on board** is how many of the board's people are already put on a mission that day — lower than Demand means the numbers are planned but not everyone is named yet. **Start from confirmed plan** fills the empty cells with the latest confirmed day's deployment (people per host and shift) as a starting point, keeping any number already typed, so each engineer only adjusts the hosts they look after. Hosts are picked from the Host list, like a mission's host. Pick 1–8 weeks ahead; right-click a cell to fill it to the end of the week, or copy the board's week forward. Like a spreadsheet, drag across cells (or Shift+click) to select a block, **Ctrl+C** to copy it and **Ctrl+V** on another cell to paste it there — the block's top-left lands on that cell, a single number fills the whole selection, and it works to and from Excel; **Delete** clears the selected cells. The **✕** on a row removes that host/shift and its numbers from today on (past days are kept). **Reset to 0** gives the next planner a clean sheet: every number the board on screen has from today on becomes 0 — in the weeks shown and any further ahead — while every host row stays and past days are kept; it asks first, names who changed it last, and cannot be undone (export first if the plan is still needed). A 0 counts as empty for **Start from confirmed plan**, so the flow *start from confirmed plan → plan ahead → reset → start again* works. **Export** (also for viewers; file type JPG, PDF or Excel in the dialog) saves the grid as **Excel** — a *working* file, one sheet per board: the yellow cells are inputs (host demand, Available people, and five spare rows for new hosts with a DAY/NIGHT pick-list), while Demand, Gap and the per-host Total are real formulas, the Gap colours are conditional formatting and each sheet has a native Excel chart (Available and Demand as columns, Gap as a line) on the same cells, so planners can keep playing with the numbers in Excel — a **JPG**, or a **PDF** (the print dialog, Save as PDF — one page, links clickable): pick one board, several or all, and add Host-list columns (**Service area, Location, Note, Google Maps link**); the days are the ones the grid shows, and every file says it is a tentative plan. The choices are remembered on the device. Viewers see the grid read-only; nothing here changes a board.
  - All of this needs `supabase/migration-2026-09-24-forward-planning.sql` (then the one-off data move `…-24b-forward-planning-data.sql` — read its header). Until they are run, none of it appears and the app works exactly as before.
- **🔓/🔒 Lock**: next to the date picker. Click it once a day's plan is finalized to make that board **view-only for everyone** — a finished plan can't be bumped by someone else's edit or an auto-refresh. Anyone can unlock it again, but they first see a popup naming who locked it (and when); confirming unlocks it for everyone, not just that person.
- **+ New Mission**: mission number, host, customer, shift (day/night) with start/end time, engineer. **Engineer** is a search, like Host: type a name and it offers everyone from **Engineer upwards** — Engineers, Managers and Admins, never Viewers — by the display name on their account, and says under the box who it has matched. Picking somebody who has never run a mission before gives them a colour of their own on the spot. The engineer's colour marks the card: full strength on its border, and a soft wash of the same colour behind the header — so you can still pick out one engineer's missions across the whole board, without the board being a wall of saturated blocks. Click a mission header to edit, delete, or hide it.
  - **Host is a search over the Host list**: start typing and the box suggests hosts, each with its service area and location. A host that isn't on the list stops the save and offers to create it — you fill in its location and service area once, and land back on the mission you were writing with the host filled in. This is what keeps "Fortune", "fortune " and "Frotune" from becoming three different sites, and it's why every mission can show where the job is.
  - The card header carries the host's **service area pill** next to the day/night chip, so the board answers "when and where" without anyone opening the mission.
  - **The host name is the map link.** A host with a location in the Host list prints its name underlined with a 📍 after it — tap it to open Google Maps. It was previously only in the Host List tab, which is a planner's screen: the one question the crew reading a shared board actually has ("where do I go?") was the one thing the board didn't answer. The link is the host's **Maps URL** when the record has one, and otherwise a **Maps search for its written address**, so a site whose record only ever got an address is still reachable. A host with neither gets no pin and no link — a pin that opens nothing would be worse than none — so filling in the Host list is what makes this appear. A long host name ellipsises but always keeps its pin. It survives into the printed PDF as a real link (see **Export / PDF**).
  - The **PPE line** on the card is the host's note plus this mission's PPE — `PPE <host note> + <mission PPE>`, the host's half in italics. A site note written once in the Host list ("gate 2, ask for Khun Somsak") then shows on every mission for that host, where the crew actually reads it. Either half alone still prints the line; with neither there's no line.
- **👁 Hide/Unhide**: takes a mission off the board without deleting its record — its definition is kept (and stays hidden as the plan carries forward day to day) until you unhide it. Anyone assigned to a mission you hide returns to Standby. Use this for a mission that's paused rather than gone for good.
- **+ New Employee**: name, contract type (Permanent = solid card with `P`, On-call = dashed card with `OC`), service area (card color). Double-click an employee card to edit.
- **Drag & drop** employee cards between missions, Leave / Standby zones, and the Available pool. (No "Return to Site" zone — since employees now belong to a specific board, sending someone back to their original board is done via right-click → Move to Board.)
- **Headcount on every leave type**: each leave zone on a board (Annual, Sick, Business, Unpaid, Exchange Working Day) shows how many people are in it, in a small pill under its name — the same idea as the headcount on a mission card. Standby and Available On-call show theirs in the floating panel. The counts go out in the JPG / PDF export too.
- **🏢 Org Chart tab**: board → engineer → service area → mission → crew for the shown day, as an Outline or a pan/zoom chart, with everyone not on a mission in a **Standby / Leave** pool under each board. Filter by **Board**, **Engineer**, **Service area** and **Standby / Leave** — the last lists Standby and each leave type with that day's headcount; untick one to leave those people out of the chart (and its crew counts and export), **None** for missions only, **All** to bring everyone back. The choice holds when you change day.
- **Resizable panel** (desktop): drag the thin handle on the floating panel's left edge to widen it (up to 60% of the window, max 760px) so the Standby / On-call cards wrap into several columns instead of one long list. Double-click the handle (or press Home) to reset; the arrow keys nudge it. The width is remembered in this browser, and the board reflows around it.
- **Search** (top-right, floating panel): filters the two unassigned pools as you type. If a match is already assigned to a mission or on leave, the box says so and flashes/scrolls to their card on the board instead of just showing "No match".
- **Stats bar**: total / assigned / leave / standby / return / available + a counter per service area.
- **Filters**: by engineer, host, customer, shift — non-matching missions fade out.
- **Manpower List tab**: every employee across every board, with a colour pill for service area matching the rest of the app, plus search/filter/sort, bulk edit (contract, position, service area, board, deactivate), a **30D utilization** column (the share of the last 30 working days that person was on a mission — counted only from the day they were added to the app, so a newcomer is not marked down for days before they existed here — as a meter plus the number — this one is per-person, so unlike the board figures above an uncalled on-call employee does count those days), a **TRIGO ID** column (searchable, sorted numerically so T9 comes before T20), a **Years of service** column and filter (under 1 / 1–2 / 2–3 / 3+ years / no start date — whole completed years from the start date to today; sorting it puts people with no start date last), and a **⬇ Excel** button that exports whatever the current search/filters are showing (there is no CSV export anywhere any more — Excel keeps Thai text, dates and links intact). **⬇ Excel** asks for the **file language** (English or Thai) and gives one plain sheet — no banner or logo, the header on row 1 in the same navy/green table design as the board export, with a total row under the table; utilization is a real percentage and the start date a real date.
  - **On the board from** (optional, on the Edit Employee form) is the day someone was added to the app. Headcount, Standby and utilization — the board, the Overview KPIs and the Trend / History charts — count a person only from that day on, so adding people later (like the 82-person LCB Port import) never changes earlier days. New employees get today's date automatically; blank means "counted on every date", which is how everyone who predates the feature stays. It is separate from **Start date**, which is the real hire date. Needs `supabase/migration-2026-10-02b-added-on.sql`, which back-fills it for everyone added on or after 2026-10-01.
  - **Bulk edit** (toolbar, needs edit rights on the list): change many employees at once in a spreadsheet. **1.** Download the **Excel template** — it holds the rows the list is showing, one per person, with a grey **ID** column (internal tracking), a **TRIGO ID** column, dropdowns for Contract type / Position / Service area / Board / Status (fed from a `Lists` sheet), real date cells, a text-formatted Mobile number column, empty validated rows at the bottom for new people, and a `Read me` sheet. **2.** Edit it and upload it back. **3.** A preview shows *To update / New / Unchanged / Problems* and, per person, every `field: old → new` before anything is written; **Apply** saves it. Rules: rows are matched by **ID** first (so a rename is a rename, not a new person), then by **TRIGO ID**, then by name — so you can fill in TRIGO IDs just by typing them next to the names; a TRIGO ID left empty keeps the current one; the Name must be a full name and a TRIGO ID must be unique (see below); only the columns present are touched, an empty cell clears Position / Mobile number / Start date (an empty *On the board from* leaves it alone), Name / Contract / Board can't be empty; people missing from the file are **never deleted** (set Status to Inactive to retire someone); a bad row is skipped with its row number and reason while the rest still apply, and re-uploading the corrected file only changes what still differs (idempotent); rows with a name not on the list are only added if you tick *Also add N new people* (a misspelt existing name would otherwise create a duplicate); a changed Board clears that person's assignment on the day you are viewing, exactly like moving them by hand; names must stay unique. It also reads Thai headers and values (ประจำ / ออนคอล / ใช้งาน…), dates as `2023-04-20`, `20-Apr-2023` or day-first `20/04/2023`, Buddhist-era years (converted), and a Thai mobile that Excel turned into `812345678` (the 0 is restored and flagged). *Download a backup of the current list first* is ticked by default: the pre-import file is itself a valid template, so re-uploading it is the undo. The same dialog is on the **Host List**: Host name (the key — renaming or merging stays in the host dialog), Status, Location, Google Maps link (must be `http(s)://`), Service area, Note; hosts not in the list yet are only added if ticked. If the list changes under an open dialog, Apply re-plans and asks you to review again. Limits: the edited **.xlsx only** (a CSV, or an old .xls, is refused with a message — CSV would lose leading zeros, dates and Thai text on its way through Excel), 5 MB, 5000 rows. Logic is in `bulk-edit.js` (pure, tested), the writes in `cloud.applyEmployeeImport` / `applyHostImport`.
  - **Thai name and English name.** Each employee has a **Thai name** (required — the Edit Employee form says it is the name the app shows by default; it is the `employees.name_th` column, renamed from `name`) and an optional **English name** (`employees.name_en`). The app uses the Thai name everywhere; the **Names** selector in the Manpower List toolbar switches that list between **Thai**, **English** (the Thai name where there is no English one) and **Thai + English** (remembered on the device), and its search finds a person by either name. The Edit Employee form **warns** ("Check the names… Save anyway?") when the Thai name has no Thai letters or the English name has Thai letters — a warning, not a block, and Cancel returns to the form with everything still typed; on an edit only a name that was actually changed is checked. The board's employee cards have the same **Names** selector in the board toolbar (Thai / English / Thai + English, the English on a third small line; remembered on the device) — it also changes what the JPG and PDF of the board show. In the **board** Excel export the **file language** decides: an English file uses the English name, a Thai file the Thai name, and whichever exists when the wanted one is empty. The **Manpower List** Excel has both columns, **Thai Name** and **English Name**, in either file language (the language only changes the headers and words; the English column is left empty for someone with no English name yet). Bulk edit has **Thai name** and **English name** columns (an empty English cell clears it; an older file with just `Name` still reads as the Thai name). `supabase/migration-2026-10-05-employee-english-name.sql` does the one-time move: Thai names stay, English-only names are copied into both columns (people fix the Thai column later), names holding both ("สมชาย ใจดี (Somchai Jaidee)") are split, and anything ambiguous is left alone and listed. It has a preview mode, runs in one transaction, keeps a backup table with the undo in its header, and **the app must be redeployed right after it runs** (the old app reads the old column name).
  - **TRIGO ID** (optional, `T` + digits such as `T329`) has its own field on the Edit Employee form, a column in the Manpower List, its own column in the Bulk edit template and in the list's Excel export, and a fixed column right after Name on every sheet of the board's Excel export (not in the column picker, so it can't be left out). The **Name** field holds the **full name only** — first name and surname, never an ID, an initial or a nickname: a new person (or a changed name) with a single word, or with a TRIGO ID typed into it, is refused with an explanation; a short name saved earlier can still be edited until someone changes it. Two people may share a name **only when both have a TRIGO ID**; a TRIGO ID belongs to one person (also enforced by a unique index). On the board, every employee card shows the ID as a small chip in its top-right corner (people with no ID yet show none); it is in the card's hover text too. The card shows the first name in bold with the surname under it, then one role chip (the position for permanent staff, **OC** for on-call) and the service area. Needs `supabase/migration-2026-10-03-trigo-id.sql`, which also **splits IDs out of existing names** ("Wannaphatson T329", "T329 Somchai", "Somchai (T329)", "Somchai - T329" → name + TRIGO ID): run it once with `apply` set to `false` to preview the report, then `true`; it only moves an ID at the very start or end of a name, skips anything ambiguous (listed as *manual* / *skipped* in the report), and saves every changed name to `employees_name_backup_trigo` with the one-line SQL to undo.
  - **Start date** (optional, on the Edit Employee form and in the list) is the first day of work. In the Excel export it comes out as a real date (`Start Date`) and as `Years of Service` — whole years, months and days from the start date to the day you export, e.g. `3 years 5 months 12 days` (Thai: `3 ปี 5 เดือน 12 วัน`); blank when no start date is on file or it is in the future. Needs `supabase/migration-2026-10-02-start-date.sql`, which also fills it in for the LCB Port roster.
- **🏭 Host list tab**: the Manpower List's counterpart for the sites you send people to. One row per host, with **Location** (an address, a Google Maps link, or both — click 📍 to open the map), **Service area** (the same colour pill used everywhere else — it's also what shows on every mission card for that host), the **inspectors ever deployed there** as chips carrying each person's day count (most days first, so "who knows this site" is the first thing you read), and **which boards** the host's missions sit on. Same search / filter / sort / **⬇ Excel** as the Manpower List: search covers host, location, service area, inspector and board names; filters are Service area, Board, Inspector and "has / has no location yet"; the two list columns sort by how many entries they hold.
  - Rows are **assembled, not stored**: every host that has ever been on a mission is listed whether or not anyone has filled in its location, so the tab doubles as the list of sites still missing one (the header counts them). **+ Host** records a site ahead of its first mission.
  - **Cleaning up duplicates and typos**: the tab flags host names that look like each other ("Fortune" / "fortune " / "Frotune" — same-after-normalising, or one edit apart including a swapped pair of letters; a differing number never counts, so "Plant 1" and "Plant 2" are left alone). **Review duplicates** filters the table to just those, each group together, busiest first. Open the wrong one and use **Merge into another host**: it rewrites the name on that host's mission and deployment rows, so the bad spelling disappears from the list *and* from past mission cards, and the two hosts' inspector day counts join up. Anything only the merged-away host knew (location, map link, area, note) carries across if the kept one doesn't have it.
  - **Archive** — the **Status** column's toggle (one click, same as the Manpower List's Status switch; also a switch inside the host record) — is for something different: a real site the team no longer serves. It keeps the host, its history and its row — dimmed, with an `archived` tag and its own Status filter — and only stops it being offered when creating a mission. Use merge for a duplicate, archive for a retired site, and **Clear record** only for details you want gone. Archiving needs `supabase/migration-2026-09-04-host-archive.sql`.
  - The **Note** column (after Service area) carries anything the crew needs to know about the site — gate, contact, a PPE reminder. It's printed, not hidden behind a hover (there is none on a tablet), it sorts and searches like every other column, it's in the Excel export, and it rides along on every mission card for that host as the first half of the PPE line.
  - **Name, location, service area and note** are the parts a person types — click ✎ (or "+ Add location" / "+ Set area" / "+ Add note") to set them. Needs the one-time `supabase/migration-2026-09-02-hosts.sql` (plus `migration-2026-09-03-host-service-area.sql` for the area); until those are run the tab still lists everything, it just can't save the details.
  - **Renaming a host** is not an ordinary edit, so it always asks first. The name is what ties the record to that host's missions and deployment history — it's also the name the New Mission form matches against — so a rename **rewrites it on every mission and deployment row the host appears on**. That's the point: the history follows the host rather than being stranded under the old spelling. The visible consequence is that **past mission cards for that host will read the new name too**. Use it to fix a typo or a capitalisation, or when a site genuinely changes its name.
    - Renaming onto a name that **already exists** is refused, and points you at **Merge** instead. That case isn't a relabel, it's two histories joining for good — it has its own confirmation and its own rules about whose location and note survive, and arriving there by mistyping a rename would be the worst possible way to trigger it.
- **Export / PDF**: two ways to take the board off the screen. Both print the same thing — the board **three mission cards wide**, with the capture header on, empty missions and empty leave zones dropped, the Standby / Available On-call pools folded in, and light theme forced regardless of who is exporting.
  - **One Export button, file type in the dialog.** Every tab (Board, Overview, Org Chart, Capacity, Manpower, Host) has a single **⬇ Export** button at the right edge of the toolbar — on a board the **Names** selector sits just left of it. It opens that tab's export dialog, which starts with **File type**: JPG image, PDF and/or Excel, whichever the tab offers (Overview and Org Chart: JPG / PDF; a board and Capacity: all three; Manpower and Host lists: Excel). The last file type picked is remembered per tab on the device.
  - **JPG image** saves a high-resolution JPG. Use it where only an image will do.
  - **PDF** opens the browser's print dialog — choose **Save as PDF**. Prefer this for sharing with the crew. It is *vector*: the text is drawn from outlines, so it stays sharp however far anyone zooms in, the file is a fraction of the size, and — the part an image can never do — **the host and phone links stay tappable inside the PDF**. It also matters how you then send it: a chat app re-encodes and downsizes anything sent down its *photo* lane, which is what makes a shared board blurry, so send the PDF (or the JPG) as a **file/document attachment** instead. Ctrl+P gives the same page as the button.
  - **Excel** saves the board's day as an `.xlsx` for planners who want to sort, filter or pass it on. It asks which **columns** to include first (Name, Contract Type, Position, Mobile Number, Start Date, Years of Service, Service Area, Mission, Host, Customer, PPE, Shift, Start, End, Engineer, Remark — all ticked to begin with), and which **extra sheets** to add, and the **file language** — English or Thai (headers, Permanent/On-call, position, shift, leave types, banner, totals and sheet names; names, hosts, customers, service areas and remarks stay as typed; a Thai file's name ends in `_TH`). All of it is remembered on that device; the Manpower List export shares the language choice. The Thai wording lives in one place, `xlsx-export.js` (`TEXT`, `VALUES`, each column's `th`, `GROUPS[...].th`), if a term needs changing. Up to four sheets, each with the same TRIGO header (navy band, logo, *Manpower Board*, board name, English and Thai date, and a big head-count) and a total row under the table:
    1. **The board name** — one row per person on a mission, missions in the board's current sort order, people permanent-first then by name. Service Area is the person's own; PPE is what the mission card shows (the host's note, then the mission's PPE).
    2. **Leave & Exchange** — everyone in Annual / Sick / Business / Unpaid Leave or Exchange Working Day, with the **Leave Type** (English and Thai); the total row counts each type.
    3. **Standby** — permanent staff with no mission.
    4. **Available On-call** — on-call staff with no mission.

    Sheets 2–4 only appear when somebody is in them, and Standby / Available On-call are skipped on a non-working day (nobody is expected in, same rule as the JPG). On those sheets Name and TRIGO ID are always kept and Contract Type / Position / Mobile Number / Start Date / Years of Service / Service Area follow the column ticks (untick Mobile Number and no sheet carries phone numbers). **Without the Contract Type column the header and total row show only the total number of employees**; the Permanent / On-call split appears only when it is ticked. The header row is frozen, filterable and repeats on every printed page; sheets print landscape, one page wide. Not offered on Overview, Org Chart or a forecast day. The workbook is built by `xlsx-export.js` (pure, tested in `tests/xlsx-export.test.js`); ExcelJS itself (~1 MB) is only fetched the first time someone exports.
  - **Three columns, whatever screen you export from.** The board used to take its column count from the window, so the same day exported as 4 columns from a 1920px monitor and 3 from a 1600px one. Both paths now pin it: they lay the board out at exactly `EXPORT_WIDTH` with `EXPORT_COLS` columns (`app.js`), so the JPG and the PDF are the same board in two formats, down to the card positions.
  - **The PDF is one single page, sized to the board** — no A4, no pagination. `setPrintPageSize` measures the laid-out board at print time and injects an `@page` rule making the sheet exactly that big (a 24-mission board comes out around 423 × 388mm; even 200 missions stays one page, at about 111 inches, against a 200-inch PDF ceiling). Two things follow from that, and they are the reason it's done this way: no page break ever falls between two missions of the same day, and because the page width is one we chose rather than one the paper imposed, the **masonry survives** — a short card still lets the one below it rise into the gap, exactly as on screen. Paper size costs nothing here because PDF text is vector: the reader zooms in as far as they like without it turning to mush. Printing it onto real A4 still works — the driver scales it to fit a sheet.
- **👤 Users and roles** (Settings ⚙ → **My account** / **Users** / **Roles**): who can sign in, and what each of them may see and change.
  - **My account** is everyone's — set your display name and change your own password. It also shows your role and status, so you can see what you have without asking anyone.
  - **Signing in**: only `@trigo-group.com` addresses can be used. Someone new is either **added** by an admin (Settings → Users → **+ Add user**, which produces a temporary password shown once, to hand over in person), or uses **Request access** on the sign-in screen — choosing their own password — and waits in a **Pending** queue an admin approves. Both ends work; use whichever suits.
  - **The app sends no email.** There is no DNS access for a sending domain, so nothing about it depends on a message arriving: no invitations, no notifications, and no "Forgot password?". Anyone signing in with an admin-issued password is made to choose their own before they reach the board, and a forgotten password is reissued by an admin from **Settings → Users → Reset password**. The trade is that the admin is the password help desk — which is why there should always be two of them.
  - **Four roles** ship as defaults, and an admin can change what any of them means:

    | | Admin | Manager | Engineer | Viewer |
    |---|---|---|---|---|
    | Board, Manpower list, Host list | edit | edit | edit | **view only** |
    | Settings — engineers / areas / boards | edit | edit | edit | — |
    | Users & roles | **edit** | — | — | — |
    | Overview — *History + Engineer workload*, *By engineer* | view | view | — | — |
    | Overview — everything else | view | view | view | view |

  - **Roles** (the matrix) is where those rules live — nineteen areas by four roles, each cell off / View / Edit. "Sensitive" is a business judgement that changes, so it is a setting rather than something that needs a code change and a redeploy. The **Admin column is locked**: it always keeps full access, so nobody can lock everyone out of this screen. Changes reach anyone with the app open straight away.
  - **Taking access away**: use **Disable**, not Delete. Disable keeps the person's record and the "locked by" / "updated by" history that names them, and only stops them signing in — the same thinking as deactivating an employee or archiving a host. **Delete permanently** really does destroy the account, and says so. Neither can be done to yourself, and the last remaining admin cannot be demoted, disabled or deleted by anyone — those rules are enforced in the database, not just hidden in the UI.
  - **What is really enforced**: reading anything needs an active account; every *write* additionally needs `edit` on that area, checked by Postgres — so a Viewer genuinely cannot change the board, whatever they try. Hiding an individual **Overview section** is different: those sections are worked out from the same mission and assignment rows the board itself needs, so it keeps the section off the page (and skips its query) rather than putting the numbers out of reach. Tidying the dashboard, not protecting a secret.
  - **Display names**: every account has one, taken from the **email address** — every TRIGO address is already *first name . last name*, so `somchai.prasert@trigo-group.com` becomes `Somchai.P`. It's the one spelling of a person that is always there and always in the same shape; an address not in that shape (or starting with an initial) falls back to the typed full name. An admin (in the user's row) or the person themselves (in My account) can type a different one when two people would collide; empty the box and the automatic name comes back. This is the name the **Engineer** box on a mission searches, and the name the board shows on a mission card.
  - Needs the one-time `supabase/migration-2026-09-04b-user-management.sql` — **edit the "REQUIRED: name the first admin" line at the bottom before running it**. Until it's run the app behaves exactly as it did before: everyone signed in has full access. Display names, the engineer↔account link and the phone number on My account need `supabase/migration-2026-09-06-display-names.sql` on top of it (no editing needed); until that is run, the Engineer box lists the engineer records alone, exactly as before.
- **Settings** ⚙ → **My account**: your **display name** — the short name the board shows you by, taken from your email address as *first name . last initial* (`somchai.prasert@` → `Somchai.P`) and yours to override if it clashes with somebody — and your **mobile number**, which is the tap-to-call link on every mission card you are the engineer for. Nobody edits your number for you. (Your full name is an admin's record of who you are; it lives in **Users**, not here.)
- **Settings** ⚙ → **Engineer**: everyone with the **Engineer** role is on this list because of their role; **+ Add engineer** puts a manager or admin who runs missions of their own on it too. The **colour** — what marks their mission cards — is set here; the name and phone come from the person's account. An engineer record made before accounts existed stays until somebody links it to one, and keeps its own name and number until they do.
- **Settings** ⚙: service areas (name, color), and each board's weekly weekend days (checkboxes, save instantly) — this drives the holiday toggle, weekend "Add Mission" import, the date picker's weekend highlighting, and both Overview trend charts, so it's worth checking a new board's checkboxes match its real schedule.

## Releasing a change

There's no build step, so the only release chore is one command:

```
node bump-version.js
```

That sets the new release version — today's date, or the next letter (`2026-10-04a`,
`2026-10-04b`) if today already had a release; pass one explicitly to override
(`node bump-version.js 2026-10-04a`) — in `version.js` and in every `?v=` on the
local scripts and stylesheet in `index.html`. Run it whenever you change any of those
files, then push. A changed URL is the one thing a caching proxy between a factory PC
and the internet cannot ignore. Don't edit the strings by hand: `node --test
tests/version.test.js` fails if `index.html` and `version.js` disagree.

Forgetting it is not a disaster: `_headers` tells every cache to revalidate on
each load, so the browser still picks the new file up. The version string is
there for the caches that ignore that instruction. If a deploy ever looks
half-updated — new page, old behaviour — check the version string first, then
hard-refresh.

### Where users see the version

`version.js` is the one place the version is written, and the app shows it so a bug
report can quote it: on the loading screen (small text under the name), under the sign-in
box, at the foot of the page, and at the bottom of the **Settings** rail (hidden on a phone,
where the footer has it).

While someone is signed in, the app re-reads `version.js` (bypassing every cache) every
10 minutes and whenever they return to the tab. If the server's version differs from the
one the page loaded, a **"A new version of the board is available"** banner appears at the
top with a **Refresh now** button. It never reloads by itself — they may be midway through
a form — and closing it stays closed until a *different* release appears. Anyone who has
the tab open for days therefore finds out; no one is left on an old version unknowingly.

## Tests

Nothing here is needed to run the app; they are for checking a change.

- `node --test tests/*.test.js` — the icon links, manifest and loading screen (`tests/icons.test.js`), the release version (every `?v=` in `index.html` matches `version.js`, and `bump-version.js` rewrites only those), the plan diff, capacity and horizon logic, and the carry-over **parity** test: the refactored carry is held to writing exactly the rows the previous code did (`tests/fixtures/copy-plan-forward.reference.js` is that previous code, frozen).
- `node tests/e2e/excel-export.e2e.js` — the Excel export in a real browser: the column and sheet pickers, the downloaded file's four sheets, the remembered choices, who can see the button.
- `node tests/e2e/bulk-edit.e2e.js` — bulk edit by file: the Excel template (ID, dropdown sheet, Read me), an unedited file changing nothing, a rename / phone / board move / deactivate applied after the preview with the backup download, CSV with a bad row (skipped with its row number) and new people held back until ticked, the host version (case-insensitive match, `javascript:` link refused, new hosts held back), and no button for a read-only role.
- `node tests/e2e/trigo-id.e2e.js` — the TRIGO ID: the Edit Employee form (full name only, ID tidied and unique, namesakes only with IDs, a short name saved earlier grandfathered), the ID on every card (no show/hide button), the Manpower List column / search / numeric sort, the Excel exports that replaced CSV (Manpower, Host, Users), and no CSV button left anywhere.

## Where is the data?

In your Supabase project's Postgres database — shared by everyone signed in. Changes
one person makes (drag a card, add a mission, etc.) sync to everyone else's screen
within a second or two via Supabase Realtime.

## Files

- `index.html` / `styles.css` / `app.js` — the app UI (no build step)
- `charts.js` — Overview dashboard charts: hand-drawn inline SVG (donut, stacked bar, bar list, line), no charting library
- `cloud.js` — data layer: talks to Supabase, keeps an in-memory cache, subscribes to realtime changes
- `planning.js` — forward-planning logic with no DOM or database: the plan diff behind *Review changes* / *Review & merge*, the confirm horizon, and the Capacity arithmetic
- `tests/` — see **Tests** below
- `config.js` — your Supabase Project URL + anon key (see `SUPABASE_SETUP.md`)
- `supabase/schema.sql` — database schema, security rules, and seed data — run once in the Supabase SQL editor
- `supabase/migration-*.sql` — incremental schema changes; run any you haven't yet in the Supabase SQL editor (each is safe to run more than once)
- `supabase/functions/admin-users/index.ts` — the one server-side function, and the only place the service-role key is used: creating a sign-in account, reissuing its password, and deleting it. Everything else on the Users screen is a plain table write under RLS and works without it.
- `icons/` + `manifest.webmanifest` — the app icon, one mark everywhere (four tiles on TRIGO blue: three white, one green): browser-tab favicons, the iOS home-screen icon, and the 192 / 512 px and maskable icons the manifest hands to Android for the home screen and launch screen. Added to a phone's home screen the app is called **Manpower Board** (the manifest's `name` / `short_name`, and `apple-mobile-web-app-title` in `index.html` for iOS). Rebuilt by `design/icons/build-icons.js`; after changing them, bump the `?v=` on the icon links in `index.html`
- the **loading screen** is `#splash` at the top of `index.html` (styled in `styles.css`): plain HTML/CSS so it paints before any script, removed by `app.js` (`hideSplash`) once it knows whether to show sign-in or the board
- `_headers` — Netlify caching rules. Everything is set to revalidate on every load; nothing is cached hard.
- `vendor/html2canvas.min.js` — library used for JPG export
- `vendor/exceljs.min.js` — ExcelJS 4.4 (MIT, licence in `vendor/exceljs.LICENSE.txt`), the library behind **Excel** export; loaded on first use
- `vendor/jszip.min.js` — JSZip 3.10 (MIT, licence in `vendor/jszip.LICENSE.txt`); adds the native chart to the Capacity Excel file (ExcelJS cannot write charts); loaded on first use
- `employee-id.js` — the TRIGO ID rules (format, splitting an ID out of a name, full-name check, who may share a name); shared by the form, `cloud.js` and bulk edit
- `bulk-edit.js` — bulk edit by file: builds the employee / host templates and plans an uploaded file (match, validate, per-field diff); no DOM, no writes
- `xlsx-export.js` — builds the Excel sheet (banner, columns, totals) from rows `app.js` hands it
- `serve.ps1` — optional local web server for development, not needed for normal use
