Final spec · Manpower Board · decided 4 Nov 2026

Mission Register: starting data, closing missions and the year-end renumber

You asked three questions. All three have the same root cause. Today a mission exists only as a copy on each day's plan, so the app has no single place that knows which missions a board has, which are still running and what each one is called. This spec adds that place, a Mission Register for each board, and shows how it answers each question. Every decision below is settled. The options you didn't pick stay greyed out so the reasoning is still visible. Nothing has been built yet.

The idea

One list of missions per board, separate from any date

Today how the code works

  • A mission is a row in missions for one board + one date. Carry over copies the last working day's rows onto the next day.
  • There is no list of "our missions" anywhere else, so a new board can only be set up one New Mission form at a time.
  • Hide pauses a mission. It carries forward hidden until somebody unhides it.
  • A mission ends when someone deletes it. That removes only that day's row. Earlier days keep it, but nothing records that the job is finished.
  • The mission number is plain text on every day's row. A renumber means editing it on the right day and hoping every later day was carried from that one.

Proposed new

  • A Mission Register for each board: one row per mission number + shift, with its host, customer, hours, engineer, PPE and a status of Open or Closed.
  • The daily board still has its own rows (so a past day stays exactly as it was), but each row points to its register entry.
  • Carry over and Start from register bring in open missions only.
  • The register is where Bulk edit by file, Close and the Year-end renumber happen, the same way Manpower and Host already work.
  • Existing boards get a register automatically, built from each board's latest working day, so nobody has to re-enter anything.
Question 1

Load a new board's missions from a file

The same three-step Bulk edit you already use on Manpower and Host: download the template, fill it in, upload it, and check a preview before anything is saved. The difference is that it fills the register, not a date. A new board's first day then starts from the register with one click.

Onboarding a new team, end to end

  1. Create the boardSettings → Boards, or + Board. Set its weekend and holidays.
  2. HostsHost tab → Bulk edit. New sites with location and service area. Exists today.
  3. ManpowerManpower tab → Bulk edit, with the Board column set to the new board. Exists today.
  4. MissionsMissions tab → Bulk edit. One row per mission number + shift. New.
  5. First dayOpen the board's first working day → Start from register. Missions appear with no crew, ready to drag people on. New.

Hosts come before missions on purpose: the mission file checks every host against the Host list, the same rule New Mission uses, so "Fortune" and "Frotune" never become two sites.

Rules, the same as Manpower and Host

  • Rows are matched on ID first, then on board + number + shift. A typo never quietly becomes a second mission.
  • Only the columns in the file are changed. A missing column is left alone.
  • A mission missing from the file is never closed or deleted. Closing is always a choice you make on purpose.
  • New missions are held back until you tick them in the preview, as new people are today.
  • A row with a problem (unknown host, duplicate number, end before start) is skipped with its row number. The rest can still be applied, and uploading the corrected file only changes what still differs.
  • The register changes straight away. A change reaches the board from the next day that is carried over or started from the register. Days already planned are left alone unless you tick Also update days already planned from… in the preview.

One number, more than one board (Q1)

  • A number belongs to one mission, and a mission can be open on several boards. The register links those rows together.
  • The Missions tab shows Also on Rayong next to a linked row.
  • A number typed on a second board is never accepted silently. The New Mission form, Bulk edit and the renumber file all ask or refuse.
  • Day and Night with the same number (Q2) are the same mission too, so they move together the same way.
  • The database checks it as well: every register row with the same number must belong to the same linked mission.

Question 2

Close a mission when the job ends

You're right that the app is missing a word. Today the team deletes a finished mission. That works on the board, but it throws away the fact that the job ended and when it ended. My recommendation is to keep Hide and Delete and add Close, giving each one a single meaning. It's the same split the Host list already uses: Archive for a site you no longer serve, Merge for a duplicate.

Where Close appears

  • The mission's right-click quick panel: Hide mission, Close mission…, Delete mission.
  • Edit Mission, next to Delete.
  • The Missions tab: one row, or several ticked at once.
  • Bulk edit: Status = Closed plus a Closed on date.
  • Year-end renumber: a Close at year end choice per mission.

Rules

  • The closing date can be today or a later day, and it can be up to 10 days back for a day that wasn't locked. Locked days are never changed.
  • A closed number can't be reused on that board for the same shift. The New Mission form says it was closed on 6 Nov and offers Reopen.
  • Overview can later count opened and closed missions per month, a figure management can't get today.

Question 3

Give every open mission its new-year number

This follows your idea: the Administrator downloads the open missions, types in the new number Finance, ERP or the customer issued for each one, and uploads the file. The column starts empty (no guesses), every row is validated, and the switch is scheduled for a date. Old days keep the old number, and days from the switch date on carry the new one, including days already carried over or forecast.

Build order

Three releases, with the renumber ready before 31 December

The year end is about eight weeks away, so the order puts the register and the renumber first. The bulk upload for new boards reuses most of what Manpower and Host already have.

Release 1
Register + Close ~2 weeks

A mission_register table (one row per board + number + shift, with a shared mission id for linked boards and Day / Night pairs), plus a link from each day's mission. A migration builds each board's register from its latest working day, safe to re-run like the others, and lists any number it finds on two boards for you to link or fix. The Missions tab (view, edit, close, reopen), the company-wide number check and the PREFIX.YY.NNNN format check, "This day only / From this day on" on Edit Mission, and permissions (Close: Engineer and up; Reopen: Manager / Admin). Carry over and Start from register skip closed missions. Delete asks "Close instead?". All of it in Thai.

Release 2
Year-end renumber needed by mid-December

Download (New number column empty), fill in, upload, validate (format, year, company-wide duplicates, empty rows) and schedule per board, Manager / Admin only. A register number history, renaming days from the switch date (linked boards and both shifts together), "was …" on the card, search by either number. Tests for planned days, forecast days and locked days.

Release 3
Bulk edit missions ~1 week

The template, upload and preview, reusing bulk-edit.js. Start from register on an empty first day. A short "Set up a new board" checklist in Settings.
