Stats bar: calmer, with a clear first read

Your instinct is right: the bar is busy. It shows 14 numbers at one visual weight, and they are three different breakdowns of the same people. Below: what is going on, four directions on identical data, and a recommendation. Everything is live: switch the day, the width, row 1 and the theme in the bar above and every mockup follows.

Findings

S1High

Fourteen numbers, one visual weight

Every chip is 11px label + 13px value in the same grey and ink. Nothing leads, so the eye has no first stop and reads the strip left to right like a sentence.

Where styles.css:569–570, app.js:2474–2488
S2High

Three breakdowns share one flat run

Status, shift and area sit in one line. Only the first seven chips get hairline separators; the area chips have none (just a 16px gap), so "Wellgrow" runs straight on from "Night". Nothing signals where one cut ends and another begins.

Where styles.css:546–547, 573–577
S3Verify

Area chips total 144; Total says 106

By my reading of the code this cannot happen on one board: Total counts rosterEmployees, the area chips count the same people filtered by area (one area each), so the areas should sum to at most Total. Either that screenshot comes from a different state or build, or area counting differs from what I read. Worth checking before anything implies "areas add up to Total". The mockups below deliberately never draw areas as part of a whole.

The code comment says Export is "always at the right edge", but its pushing spacer only works on the same line as the stats. Keep: what already works

  • Labels are spelled out, never abbreviated or icon-only. Keep that.
  • Tabular numerals on every figure, so columns of counts don't jitter between days.
  • One control height (32px) and one radius across row 1: the rhythm is good.
  • Read-only is amber with a lock icon and words, so it never relies on colour alone.
  • "Total = Assigned + Leave + Standby + On-call free" and "Day + Night = Assigned" are real invariants (verified above); the directions below use them.
2 · Four directions

Same data, four ways to read it

Each direction changes only the stats cluster (and, where noted, where the area counts live). Numbers, labels and the sample day are identical in all four, and Row 1 follows the control above. Try Short-staffed to see how each one flags the count that matters, and Holiday for the extra chip the app adds on non-working days.

A

Grouped & hushed

Smallest change

Same single line, same 14 numbers, but with a hierarchy: number first, three labelled groups, and zeros that fade.

Direction A toolbar height –

What changes

  • Number first, label second, no colons: planners scan for the figure.
  • Three groups (People · Shift · By area), one divider each, instead of seven hairlines and an unmarked run.
  • Zero fades to muted. A non-zero Standby becomes a tinted tag with an alert icon.
  • Night dot becomes Day / Night icons (shape plus text).
  • Labels go from 11px to 12px; area counts get a small "By area" caption.

Gains

  • Lowest risk: same information, same position, same line count.
  • Every number stays glanceable.
  • The exception (Standby > 0) finally stands out.

Costs

  • Still 14 numbers: calmer, not fewer.
  • The "parts of Total" relationship stays implicit.
  • Below ~1300px the area group wraps to a second line.

Effort

Small. renderStats markup plus about 40 lines of CSS. E2E tests read chip text as "Label: n" (added-on.e2e.js:25), so they need a one-line update.

B

Headline + composition bar

Recommended

One headline ("83 of 106 assigned") and a single bar that shows how the 106 split. The sum-to-Total relationship becomes visible instead of something to work out.

Direction B toolbar height –

What changes

  • "83 of 106 assigned" leads. It is the first read the board owes you.
  • A stacked 100% bar for Assigned / Leave / Standby / On-call free (plus Holiday on non-working days). Each segment is labelled with its number in the legend; colour never carries the meaning alone.
  • Status is the headline line. Day / Night and By area become one quiet second line, because they are secondary cuts of the same people.
  • Areas are not drawn as a bar, because they don't reconcile with Total (S3).
  • Standby > 0 makes its segment appear and its legend item turn red with an alert icon.

Gains

  • Clearest hierarchy of the four without hiding any number.
  • You see "nobody is idle" or "9 people have no job" before reading a digit.
  • Frees row 2's right side: Export / Read-only stay on the same line as the stats.
  • The second line can later become filter chips for shift and area (see the note at the end).

Costs

  • One new component (the bar) and an accessible name for it.
  • Day / Night and areas sit on a second, thinner line, so they are a glance lower than the headline.
  • Not shorter than today: about the same height at 1280 (live height above). It spends the space on hierarchy, not on saving it.
  • Zero-width segments are omitted, so the bar alone can't say "Standby 0"; the legend does.

Effort

Medium. renderStats + a small bar helper + CSS. The bar is a flex row, so no charting library is needed. Same e2e text-match update as A.

C

KPI tiles

Bold

The four counts a planner works from become tiles with large numerals; Day / Night live inside the Assigned tile.

Direction C toolbar height –

What changes

  • Total as a lead figure, then four tiles: Assigned (with Day / Night), Leave, Standby, On-call free. A Holiday tile joins on non-working days.
  • 22px numerals with a colour edge, plus the label, so state is never colour alone.
  • Standby tile turns red with an alert icon when non-zero; zero is muted.
  • Areas drop to the same quiet second tier as B.

Gains

  • Strongest hierarchy; readable across a room (design principle 4, shop-floor displays).
  • Each tile is a natural click target if you later want "click to filter".

Costs

  • The tallest option (about 15px more than today at 1280; live height above): the tiles are about 46px high where a chip line is about 26px. That runs against the "density is a feature" principle.
  • Four tiles read like a dashboard: heavy for a toolbar that sits above the board.
  • On a phone the tiles wrap to two rows.

Effort

Medium. New tile markup and CSS, same e2e update.

D

Summary line + details popover

Calmest

One sentence in the bar; everything else one click away. The popover is open here: click Details to close it.

Direction D toolbar height –

What changes

  • The bar keeps three facts: assigned of total, leave, standby (plus holiday when it applies). Standby is flagged in red when non-zero.
  • A Details button opens a popover with On-call free, Day / Night and By area.
  • Toolbar is two lines at any normal width.

Gains

  • Quietest and shortest: two lines at every desktop width, so the board starts about 30–40px higher than today (live height above).
  • Best phone story: a short line plus a sheet.
  • The app already has a popover pattern (.ms-pop) to reuse.

Costs

  • Day, Night, On-call free and areas are no longer glanceable: a click away. If planners check Day / Night all day, this will annoy them.
  • Popover needs focus handling, Esc and outside-click.
  • The old code comment explicitly rejected hiding counters; here it is an explicit control rather than a silent scroll, but it is still hiding.

Effort

Medium to large. New popover content, keyboard handling, phone sheet, e2e rewrite for the hidden counts.

Recommendation

Direction B, plus the row-1 tidy. It is the only option that makes the stats less busy and more informative at once, because it shows how the numbers relate instead of just restyling them, and it keeps every number visible. It also lets the toolbar settle back to a predictable shape, with Export at the right edge.

If you want the smallest possible step, ship A first: B reuses A's zero-fading, icons and area tier, so A is the first half of B, not a detour.

Decisions I need from you

  1. Which direction (A, B, C or D), or a mix?
  2. Apply the row-1 tidy too (section 3), or leave row 1 alone for now?
  3. Areas: keep as a quiet second tier (B, C), fold into a popover (D), or later make them filter chips?
  4. S3: can you confirm whether area counts are expected to add up to Total? I would settle that before building anything.

When we implement

  • Touch points: renderStats and statChip (app.js:2404–2489), the stat-chip CSS block (styles.css:539–596) and the phone overrides (styles.css:1468–1473).
  • .stat-chip is also used by the Manpower, Host, Capacity and Org Chart tabs, and by the bulk-edit preview, so keep those on the old chips or migrate them together.
  • E2E tests read "Label: n" from #stats-bar .stat-chip (added-on, forward-planning); update them in the same change.
  • Holiday adds a chip; forecast days use the same stats; Overview shows no stats on purpose. All three are handled in the mockups' scenarios or unchanged.

Beyond this review, not mocked: clicking a stat or area to filter the board. It would be a natural next step for B or C, but it is new behaviour and needs a product decision.
