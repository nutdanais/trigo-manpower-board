Summary

Two paid plans cover all three apps for about USD 30 a month, with room for at least 5 years at today's size.

Decision asked for: approve Cloudflare Workers Paid for hosting all three apps and for the Approval and Inventory data, and Supabase Pro for Manpower Board's data, both on company accounts and a company card.

  • Why Cloudflare: Inventory is already live there, and the Approval app is not built yet, so changing an unbuilt app's plan is cheaper and safer than moving a working one.
  • Why Manpower Board stays on Supabase: it depends on Postgres features Cloudflare's D1 database lacks (row-level security, triggers, live updates). Moving it would save USD 1,500 over 5 years but take weeks of rebuilding.
  • What it unlocks: PO deliveries confirmed once, in the app where the goods arrive, and seen by both apps; one login for staff; one vendor, user and item list. Manpower Board gets daily backups and no free-tier pause.
  • What changes: section 07 of the Approval spec and answers Q26 to Q28 of the Requirements Confirmation Report; Inventory gains "Receive against PO" and reads shared master data; Manpower Board moves its pages from Netlify to Cloudflare Pages and its Supabase project to a company-owned organisation.

Target architecture

Every app has its own Pages site in one TRIGO Cloudflare account. Approval and Inventory share a sign-in, a core database and private file storage; Manpower Board keeps its data on Supabase.

The Approval and Inventory Workers call each other through a service binding, a private link inside the account, so neither app exposes an integration address to the internet. Manpower Board's pages talk to Supabase directly, as today: row-level security decides who sees what, and Realtime pushes each change to every open board.

Changes to each app, data and security

Approval changes its technology plan, Inventory gains two features, and Manpower Board changes where it is hosted and who owns its accounts, not how it works.

Manpower Board

  • Pages: move from Netlify to Cloudflare Pages on the TRIGO account, built from GitHub on every push; config.js is generated from the project's environment variables, as on Netlify today.
  • Previews: each pull request gets a Pages preview link, so the /?demo previews keep working.
  • Database: transfer the Supabase project into a TRIGO organisation on Pro. Tables, row-level security, Realtime and the admin-users function stay as they are.
  • Sign-in, later and optional: once Approval is live, Manpower Board can accept the shared Firebase sign-in through Supabase's third-party auth, so one login works in all three apps.

Inventory

  • Request purchase: pick low-stock or chosen consumables, set quantities and a requester, and send them to Approval as a draft PR; follow its status and the quantity on order per item. A weekly draft of all low-stock items is prepared automatically.
  • Receive against PO: pick an expected delivery, lines pre-filled, record actual quantities with short or over differences, lot and expiry as today.
  • Shared master data: the supplier field becomes the shared vendor list; users, departments and warehouses come from the core database.

Document Approval spec

  • Hosting (Q28): Netlify becomes Cloudflare Pages + Workers. Database (Q26, Q27): Supabase becomes D1 with an Asia-Pacific location hint, permissions checked in the Worker. Sign-in: the shared Firebase project.
  • Scheduled jobs move to Cloudflare Cron Triggers; files stay in R2; email stays Brevo or Resend; the PO PDF on Workers is proven in the first sprint.
  • The PO continues to delivery: "Deliver to" per line, receipts, PO closed when all lines are received. Vendors become their own module.

Security, location and backups

  • Ownership: the Cloudflare account, the Supabase organisation and a GitHub organisation belong to TRIGO Thailand, billed to a company card, with at least two administrators using two-factor sign-in.
  • Permissions: D1 has no row-level security, so each Worker checks role, position and route before reading or writing, with automated tests before go-live. Manpower Board keeps its row-level security in Supabase.
  • Files and audit: private R2 buckets opened only through the Worker; every create, edit, approve, view and download logged and kept 3 years.
  • Backups: D1 restores to any point in the last 30 days, plus a weekly export to R2. Manpower Board gets Supabase Pro daily backups kept 7 days, plus the same weekly export.
  • Data location: D1 takes an Asia-Pacific hint but does not guarantee a country; Legal or IT must confirm this under TRIGO policy and Thai PDPA. A Supabase project stays in the region chosen when it was created, so check which region Manpower Board uses today.

Steps to start moving

Start with company-owned accounts and Manpower Board's backups, then move the live apps one at a time; each step ends in a check before the next starts.

  1. 1

    Approve

    Agree this plan and the 5-year budget; name the account owner and a second administrator.

  2. 2

    Company accounts week 1

    Create a shared admin mailbox on trigo-group.com, then a Cloudflare account on Workers Paid, a Supabase organisation on Pro and a GitHub organisation, all on a company card, each with the two administrators and two-factor sign-in.

    Check: both administrators can sign in to all three.

  3. 3

    Manpower Board database weeks 1–2

    Transfer its Supabase project into the company organisation; the project and its data stay where they are, and it moves onto Pro with daily backups.

    Check: the board works unchanged, the first daily backup is listed, the region is noted.

  4. 4

    Repos week 2

    Transfer the three GitHub repos to the organisation; GitHub redirects the old links.

    Check: tests and deploys still run.

  5. 5

    Manpower Board pages weeks 2–3

    Create a Cloudflare Pages project from the repo with Netlify's environment variables and preview links on. Run both addresses for a week, then send staff to the new one and close Netlify.

    Check: staff sign in on the new address; /?demo works on a preview link.

  6. 6

    Inventory weeks 3–4

    Move its Pages project, Worker, D1 database and R2 bucket into the company account (export and import D1, copy R2), then switch the address.

    Check: Inventory runs unchanged; a restore from backup works.

  7. 7

    Backups week 4

    Weekly exports of every D1 database and of Manpower Board's Supabase database to R2.

    Check: one test restore from each.

  8. 8

    Shared core

    Create the core database (users, departments, sites, warehouses, vendors) and move Inventory's users onto it.

    Check: Inventory sign-in and permissions unchanged.

  9. 9

    Approval app, first sprint

    Build sign-in, permissions and the PO PDF on Workers first.

    Check: PDF and permission tests pass; data location confirmed by Legal or IT.

  10. 10

    Approval app, full build

    PR, PO, documents, vendors, delivery tracking, settings, audit trail; turn on Resend Pro.

    Check: user acceptance test with Purchasing, Finance and one warehouse.

  11. 11

    Integration and go-live

    Expected deliveries, Receive against PO in Inventory, receipts back to Approval.

    Check: one month of POs received end to end without double entry.

  12. 12

    Later, optional

    Manpower Board accepts the shared Firebase sign-in.

    Check: one login opens all three apps.
